The idea in one minute

Red Stack is a mod manager for Cyberpunk 2077 that lives in VS Code. It starts from one simple idea: your folder of zips is the library. You file your downloads the way you like; Red Stack reads them where they are, without copying them elsewhere or reorganising them.

Five words are enough to understand everything else:

RepositoryThe folder where you keep the zips of your mods.
StackA subfolder of the repository (for example 1_Core, 12_Weapons). The page shows one table per stack.
ProfileThe list of what you want in the game: which mods are enabled, which options and which files of each. You can have several.
StoreA working folder where each enabled mod is extracted into its own tree. The game files are links to these trees: a mod takes its space on the disk only once.
PlanThe difference between what the profile wants and what the game contains: what would be installed, replaced, removed.
The rule that never changes. Ticking a box only writes the profile. The game is written only by Apply, after you have read the plan preview and confirmed, and only the plan you saw is applied. Every action that writes the repository or the game is confirmed in a list at the top of VS Code, whose first choice, selected by default, is “Write nothing”.

Getting started

  1. Python 3.11 or later must be installed on the machine: the Red Stack engine is a Python script shipped inside the extension. Nothing else to install. Red Stack tries python, then py -3 and python3; if it finds none, the page says so and offers to download it or to set its command.
  2. Open the page: the Red Stack icon of the activity bar (on the left), the “Red Stack” button of the status bar (at the bottom), or the command Red Stack: Open (Ctrl+Shift+P).
  3. On first launch, the “Settings” page asks for two folders: your zip repository and the game folder. Save.
  4. The page then offers to read the game to create the profile “actuel” (current). This reading writes nothing: it recognises in the game the files of your zips and ticks the mods that are already there.
  5. Read the Plan preview. On a game that is already modded, the first plan mostly replaces copies with links to the store. Apply, with the game closed.

After that, the routine is three actions: tick or untick, read the plan, apply.

If your repository does not follow the expected layout (which folders are stacks, where parked or new zips go), it can be set: see Settings, “Repository convention”. Loose zips in a single folder work too: those placed at the very root of the repository are read as one more stack, “(repository root)”.

The mod list

The page opens on the list: one table per stack, one row per zip.

The header

  • Profile: the profile shown. New… copies the current profile under another name, Delete erases the profile file (the game does not change).
  • Filter mods…: filters by name, as you type.
  • Which mod owns this file?: type part of the path of a game file, then Enter. Red Stack says which mod installed it.
  • Arrivals, Updates, History, Store: managing the repository.
  • Conflicts, Scripts: the two analyses, each in its own tab.
  • Settings, ? (this manual), ↻ (re-read now; hovering it gives the time of the last reading), Plan preview.

The checkboxes

  • The checkbox of a row enables or disables a mod. The checkbox of a stack title enables or disables the whole stack.
  • You can tick several mods in a row: Red Stack waits for a short silence, then plays all your ticks together and re-reads the state only once. No tick is undone on the way.
  • While an action is writing (park, move into the stack, retire, rename, apply…), a banner says so and the page is locked from the confirmation to the end of the action: nothing can be ticked or clicked. It unlocks on its own.
  • A click on the title of a stack folds or unfolds it. A click on a row opens the detail of the mod.

The “State” column

installedEnabled, and the game holds its files. “(modified in game)”: one of its settings has changed since it was installed; it is kept as it is.
to installEnabled in the profile, not in the game yet. Waiting for “Apply”.
to completeAlready installed, but the plan still has files to install or to replace for it (option added, new version).
disabled, to removeUnticked, its files are still in the game. Waiting for “Apply”.
disabledUnticked by you, out of the game.
never installedKnown to the profile, never entered the game.
new in the repositoryA zip that arrived in a stack and that the profile does not know yet. Unticked by default (this can be set).
parked, retiredA zip filed in the parked folder or the retired folder of its stack: visible, not installable until it is moved back into the stack.

The “Kind” column

What the zip installs, read from its content: archive, xl (ArchiveXL), REDmod, scripts (Redscript), tweaks (TweakXL), CET, RED4ext, asi, audio, ReShade, settings, other. A click on a chip filters the list on that kind; a second click shows everything again.

Core marks a mod that others depend on: it ships a loader (CET, RED4ext, Redscript, ArchiveXL, TweakXL, Codeware), or other mods of the repository call it in their code. Limit: a core mod used without a call that can be read in the code is not recognised as one.

Badges, chips and sorting

  • ▼ ▲ on a row: this mod loses or wins resources against other archives. ⇄: its own archives overlap each other. Hovering gives the detail, a click opens the conflict analysis on this mod.
  • The FOMOD chip marks a zip installed by its installer.
  • The ⚠ requirement chip (red) marks an active mod that lacks a framework (Cyber Engine Tweaks, RED4ext, redscript…): it will not load. The requirement? chip (amber) marks that a mod the author lists as required on Nexus is not active. The Requirements to check filter shows only these mods; the detail of the mod says what is missing.
  • The chips under the header filter by state; the line of figures sums up the profile. New shows the zips of the arrival folders and those of the stack that the profile does not know yet; Parked and Retired show the content of the parked and retired folders.
  • A click on a column header sorts; the third click restores the order of the repository.
  • ⇕ Fold / unfold all, on the line of figures, folds every stack at once; if everything is already folded, it unfolds everything. In “Updates” and “Arrivals”, it folds the stack bands. The same button folds the rows of the “Conflicts” and “Scripts and tweaks” tabs, and a ⇕ at the top of a panel does the same for its rows (history, plan, folders in the detail of a mod).
  • Detail of a mod: its files are sorted by path. Those of a pack, or of a mod of more than forty files, are grouped in foldable folders, each with its count of files taken; an unfolded folder stays so when the list is redrawn. An unticked file whose target is installed by another folder of the same zip is said to be “held by another folder of this zip”: nothing leaves the game.
  • Width of the panel: drag the edge between the list and the panel to widen or narrow it; a double-click on that edge goes back to the original width. The width is kept.
  • Full names shows the whole name of the zip instead of the title read from a Nexus download name. Folders shows where a parked, new or retired zip is. Kinds shows or hides the “Kind” column: unticked, it gives its width back to the names.
  • At the end of a row: park a mod that is disabled and out of the game; for a filed zip (arrived, parked, retired), move it into the stack, park an arrival, or retire it (the bin): the zip goes to the retired folder of its stack. Each action is confirmed and is only a move of the zip inside its stack: nothing is erased, a retired zip is moved back from the “Retired” filter. In that filter only, the bin deletes the zip: it leaves the repository for the Windows recycle bin. The choices of the mod stay in the profile for its return.
  • Several filed zips at once: in the “New”, “Parked” and “Retired” filters, each filed zip has a checkbox, and the checkbox of a stack ticks all those of the stack shown on screen. These checkboxes never touch the profile or the plan. As soon as a zip is ticked, the buttons Move into the stack…, Park…, Retire…, Delete… (retired zips only) and “Untick all” appear to the right of the chips; the lot goes in a single confirmation, and the boxes stay ticked until the action ends.

Profiles

A profile is a file that says what you want in the game. Changing profile only changes what the page shows: the game follows when you apply the plan of that profile.

  • The profile keeps, for each mod: enabled or not, the options of a pack, the files taken one by one, the choices of a FOMOD installer, the names changed in the game, the priorities between mods and the wanted load order.
  • New… always starts from a copy of the current profile: handy for trying a batch of mods without losing the state that works.
  • Going from one profile to another means reading the plan (what comes in, what goes out) and then applying. Thanks to the links, this takes a few seconds even for hundreds of mods.

The detail of a mod

A click on a row opens the detail: everything the zip contains, where each file goes in the game and in what state it is there.

States of a file

linkedThe game file is a link to the tree of the mod in the store.
copiedInstalled as a copy: this is the case of settings (so that they survive an update) and of files in the territory of a third-party installer.
shared with XAnother enabled mod ships the same file, identical: it stays in the game as long as one of the two is enabled.
overwritten by XAnother enabled mod ships a different file at the same place, and its file is the one installed.
modified in gameThe file has changed since it was installed (a setting written by the game or by you). It is kept, never silently replaced.
outside Red StackThe file is in the territory of a third-party installer (ReShade…) and Red Stack did not install it: it leaves it alone.

Choosing what to take

  • Pack with options: a zip that files its variants in folders shows them as options to tick.
  • One checkbox per file: take or leave a single file. The game only changes at “Apply”.
  • “This file belongs to this mod”: on an “outside Red Stack” file, ticking the box says that this file belongs to the mod. Red Stack records it in its registry without modifying it, and it will leave with the mod when you disable it. Unticking hands it back to the third-party installer and leaves it in the game.
  • Priority between two mods: when two enabled mods want the same file with a different content, the plan stops on a conflict to settle. You say which one wins, file by file or for the whole mod; the profile remembers.

Requirements

The detail says what the mod needs to work, which zip of your repository provides it, and in what state. Two sources:

  • Listed on Nexus: the list the author gives on the mod page. It is read along with the updates (“Updates” view), or for a single mod with Read on Nexus; no API key is asked for. Nexus gives no minimum version, and authors also file there what they merely recommend: only their note tells. Red Stack marks as “optional” a requirement whose note suggests so, and never counts it as a fault.
  • Deduced from its files: a framework is recognised by where the zip puts its files (a Lua script in the mods folder of Cyber Engine Tweaks, a .reds under r6/scripts, a tweak under r6/tweaks, an .xl, a plugin under red4ext/plugins, an entry under r6/input, a sound under r6/audioware, a REDmod). This reading does without Nexus: it also holds for a mod with no number.
activeAn active zip of the profile provides it.
in the game, outside Red StackThe framework is in the game without Red Stack having installed it (by hand, or by another manager): it is taken as present.
disabledThe zip that provides it is in a stack, but disabled in this profile.
put awayThe zip that provides it is only parked, or in an arrivals folder.
missingNo zip of the repository provides it. Its name opens its Nexus page.
outside NexusA requirement from outside Nexus (ReShade…) or from another game: Red Stack cannot check it.

“Required by” lists, the other way round, the mods of the repository that need this one; a disabled mod that active mods require says so in red. A requirement you hold under another zip (a pack, an edited version with no Nexus number) is still shown as “missing”: Red Stack recognises a Nexus mod only by the number carried in the zip name. In that case, or if you do not want it, Ignore on its line silences it for this mod: it stays listed, marked “ignored”, raises no chip and no warning in the plan any more, and the choice follows the mod from one version to the next; Stop ignoring brings it back.

The buttons of the detail

  • Installer…: the choice pages of a FOMOD.
  • Rename the zip…: changes the name of the zip file in the repository. The profile, the store tree and the registry follow; the game is not touched. Keep the Nexus number in the name if you want to keep the updates and the requirements read on Nexus.
  • In-game names…: install the files of the mod under other names, without touching the zip.
  • Rename the content…: rewrite the zip with names that follow your convention.
  • Archive conflicts…: the conflict analysis, centred on this mod.
  • The Nexus link opens the page of the mod when the name of the zip carries its number.

Plan preview and “Apply”

Plan preview compares the profile with the game and lists what would be done, without writing anything:

to installFiles missing from the game, brought by an enabled mod.
to replaceFiles present with another content (new version, another mod with priority).
to removeFiles of a disabled mod that no enabled mod ships any more.
to link / to unlinkAn identical copy becomes a link to the store, or the reverse (a file that became a setting or moved into third-party territory). The content of the game does not change. After an update, the files that stayed identical from one version to the next are “to link”: they move to the tree of the new version, nothing is copied. A “to link” taken over from another mod says which one. Under each mod of the plan, “Show the files” lists the touched files one by one; the block of choices made folds with a click on its title. The details of a mod being updated say “to replace” or “unchanged since the previous version” instead of naming its own old version.
taken / handed backA file recorded in the registry by “this file belongs to this mod”, or handed back to the third-party installer.
modlist.txtThe load order file to write or to remove, if the profile holds it.
conflictsTwo enabled mods want the same file, different content, with no priority given. To settle before applying.
disabled modsOne line per disabled mod: what leaves the game, what another mod takes over as it is, what another already holds.
requirementsThe active mods that lack a framework, and those for which a mod listed as required is disabled in this profile. Nothing is blocked: it is a warning before writing.

Apply

  • Apply to the game… opens a list at the top of VS Code. The first choice, “Write nothing”, is selected by default: Enter alone never writes the game. You have to go down to “Apply” and then confirm.
  • The game must be closed. If it is running, nothing is written.
  • If the disk has changed between the preview and the click, the plan is no longer the one you saw: nothing is written and the new plan is shown to you.
  • A file modified in game since it was installed (a setting, most often) is kept as it is: the plan counts it apart and “Apply” does not replace it.
  • File present but not installed by Red Stack: the game already holds this file, which Red Stack did not put there, with another content than the one in the zip (a mod installed by hand in another version, for example). It is left in place. To take the one from the zip, unfold this line of the plan: Replace with the zip on one file, or Replace all with the zips. The file then moves to “to replace”; when applying, the old one is first copied to the backups folder. Leave in place goes back as long as nothing is applied.
  • Taking over a mod installed by hand: drop its zip in the arrival folder of its stack, move it into the stack, tick it, open the plan preview. Identical files are taken over without writing anything; the others are replaced as above.
  • The “Before applying” command of the Settings, if you have set one, is run first; if it fails, nothing is written.

Arrivals

Arrivals shows what has just entered the repository: the archives of the arrival folders of each stack, the zips that still carry a name from the Nexus app, and the .7z / .rar files. The rows are grouped by stack, in the order of the mod list; a click on the band of a stack folds or unfolds it.

Bringing names to the form of the site

  • For each archive, Red Stack proposes the name the Nexus site gives: Name-modId-version-timestamp.zip. It reads it through the public Nexus API, without a key, and keeps the answer for six hours (Re-read Nexus asks again).
  • This is the name that later makes it possible to look for updates.
  • The proposed name can be edited in its field. When several files of the mod fit, the row is “to settle”, with the list of candidates.
  • Tick the rows, then Rename the ticked archives…. Only the file name changes.

Convert, move into the stack, park

  • Convert to .zip…: a .7z or a .rar is rewritten as a .zip (by 7-Zip, UnRAR or the Windows tar), read back, then the original is deleted. Several archives convert at once: tick them, then “Convert the ticked ones…” at the top of the view; one confirmation, and an unreadable archive does not hold back the others. Likewise, “Content of the ticked ones…” renames in one go the content of all the ticked zips, to the names Red Stack proposes; to edit a name, go through “Content…” on the line of the zip.
  • Move into the stack…: the zip leaves the arrival folder and becomes a mod “new in the repository”, to tick in the list.
  • Park…: the zip goes to the parked folder of its stack.
  • “Move the ticked ones into the stack…” and “Park the ticked ones…” handle a lot in a single confirmation.

Recognising an update

When an arrival is a more recent version of a mod already in place, the row says so. File the update… puts the new zip in place of the old one, which goes to the retired folder of its stack; the profile follows the new version. “In place of…” lets you name another zip of the same mod. This action needs no API key: downloading the file by hand into an arrival folder is enough.

Mod without a Nexus number (your own mod, a zip from GitHub): Red Stack recognises it by its name and its version. An arrival My Mod 1.0.1.zip is proposed as the update of My Mod 1.0.0.zip (spaces, dashes and capitals do not count; the version must be higher). The new zip keeps its name. These zips do not appear in “Updates”, which only reads Nexus.

Naming the replaced zip yourself: when Red Stack recognises nothing (name changed, no version in the name), the File in place of… list of the row offers every zip in place in the same stack. Choose the one the arrival replaces: nothing is compared, the arrival takes the name of the “Wanted name” field, the old zip goes to the retired folder. A confirmation comes before the writing.

“Content…”: the names inside the zip

  • Content… proposes to rename what the zip ships (archives, .xl, script and tweak folders) according to your convention: capitalised words, name of the mod, useless top folder removed.
  • Before proposing, Red Stack reads the references of the whole repository. A name hard-coded in some code, a folder shared with another mod, a load order prefix are kept, with the reason shown.
  • Each proposed path can be edited. The proposal recommends, it does not block you.
  • Restructuring: an edited path can change folder. Type it in full (r6/tweaks/Family/My_Mod.yaml): a folder that does not exist is created in the zip. Nothing checks what the mod expects at that place; that is for you to know.
  • Add the folder does this for scripts and tweaks: the name typed in “Folder to add” is inserted right under r6/scripts and r6/tweaks, in every path of the table. Nothing is written: you read it again, then you rename. Archives are left alone, the game does not read them in a subfolder.
  • Family folder: when at least two other zips of the repository whose names start the same way (Family - …) keep their scripts or their tweaks in one same subfolder, Red Stack proposes it for those of the newcomer, and says so.
  • Confirming rewrites the zip (same files, same dates, new names), reads it back, then replaces the old one. If the mod is in the game, the plan will replace its files.
This action is different from “In-game names…”, which does not touch the zip and only records in the profile under which name to install. “Content…” tidies your repository; “In-game names…” settles one case in one profile.

Updates (Nexus)

Updates compares each zip named in the form of the site with the files its mod publishes on Nexus. The search needs no key and downloads nothing. The rows are grouped by stack, in the order of the mod list, then by name; a click on the band of a stack folds or unfolds it. A zip without a Nexus number (your own mod) is not compared: its new version is filed from “Arrivals”.

Reading the list

  • Update: a more recent file, with the same name apart from the version and in the same category. Ticked by default.
  • To check: a doubtful case (file archived by the author, several candidates, variant for another patch of the game). Never ticked by default; the row lists the more recent files to choose from.
  • A zip that you annotated in its name (your own edit) is proposed but not ticked, with a warning: the update would replace your edit.
  • Ignore leaves a mod out of the searches; it can be undone from the same view.
  • The name of the new zip can be edited before downloading.
  • Not compared: zips without a mod number in their name, and mods published elsewhere than on Nexus.

Downloading

Downloading needs your personal Nexus API key:

  1. Nexus API key… opens an input box in VS Code. Where to find it? opens the keys page of your account: the personal key is at the very bottom of that page, under the list of applications (“Personal API Key”).
  2. The key is kept in the VS Code secret storage. It is written in no file and is never given to the MCP server. An empty field forgets it.
  3. Tick, then Download…: one confirmation for the lot, then the zips arrive one by one.
  • Each new version takes the place of the old one, which goes to the retired folder of its stack. The profile follows. What remains is to read the plan preview and apply.
  • Premium account: direct link, nothing else to do.
  • Free account: Nexus reserves the direct link for Premium accounts. For each zip, Red Stack opens the page of the file; you click “Mod manager download” (or “Slow download”). The link arrives on its own if Red Stack is registered for nxm:// links; otherwise you paste it in the box opened at the top of VS Code.
  • During a download, the view is locked (one lot at a time) and the zips concerned can be neither parked nor rewritten. The rest of the tool stays free.
The quota of API calls is attached to your key, and so to your account. The chip of your account, on hover, says what is left of it.

nxm:// links (“Mod manager download”)

On Nexus, the “Mod manager download” button sends an nxm:// link to the mod manager registered on the machine. Red Stack can be that manager (Windows).

  1. Settings, “This machine” section: the page says which program receives these links today.
  2. Receive nxm:// links in Red Stack… (confirmed) writes one key in the registry of your Windows account, without administrator rights. The previous program is recorded.
  3. Stop receiving nxm:// links… undoes the registration and hands over to the previous program.

Once registered, a click on “Mod manager download” opens a list of choices in VS Code:

  • Update such a zip of the repository: the file received is from the same mod. The new version takes its place.
  • New mod: choose the stack; the zip is filed in its arrival folder and appears in Arrivals.
  • Download nothing, the choice selected by default.

The API key is still needed: Nexus does not deliver the file without it, even with the link.

FOMOD installers

A zip that carries fomod/ModuleConfig.xml describes its own installation choices. Red Stack replays that installer.

  • In the detail of the mod, Installer… opens a panel with its pages, its groups (exactly one choice, or several), the descriptions, and the images on demand.
  • A click records the choice in the profile. The pages and the files that depend on a choice follow at once; a page ruled out by an earlier choice is said to be hidden.
  • The files the installer copies outside the game folders (documentation, tools) are installed by default, as any installer would do; a checkbox lets you leave them out.
  • “Ignore the installer: pick by hand” gives the zip back to the per-file checkboxes. Follow the installer returns to it.
  • As always, the game only changes at “Apply”.
Limits, also stated on screen. A condition on the presence of a file in the game is taken as “missing”; a condition on the version of the game is taken as true.

In-game names

In-game names… (detail of a mod) installs what the mod ships under other names: archives, .xl, files and folders of r6\scripts and r6\tweaks, CET folder, REDmod folder.

  • One field per name. The zip does not change: the profile records the wanted name; “Apply” installs the new one and removes the old one. An emptied field restores the author's name.
  • Each row says who quotes this name in the code of the repository, the mod itself included. A quoted name is a name that some code looks for as it is: renaming it can break the mod that quotes it. Red Stack warns, without blocking you.
  • Refused: a change of case alone, and a name that would take the place of the file of another enabled mod.
  • A renamed CET folder leaves its settings written in game under the old name.

Common use: changing the place of an archive in the load order (see below), or tidying the script folders of a family of mods.

Archive conflicts

Several archives can ship the same resource (a mesh, a texture). The game takes each resource from the first loaded archive that contains it. So an archive wins over those loaded after it and loses against those before it.

On screen, “archive” means the .archive file and “resource” what it contains.

Conflicts opens the analysis in a tab beside the page (it can be detached into a window by a right click on its title). It is read-only, done on the order wanted by the profile; a chip says how many archive changes are still to apply.

Four readings

  • Per archive: for each one, over whom it wins and against whom it loses, in number of resources.
  • Per mod and per mod pair: “A wins over B”, with “show all” for the list of resources.
  • Each row says how many resources the mod or the archive delivers, and how many are still served to the game. With the row unfolded, All its resources… adds the list of those outside any conflict: it is alone to deliver them, so the game takes them from it. A second click hides it.
  • Per archive pair.
  • Per resource: in which archive it is taken, by which ones it is lost.
  • The chips with figures can be clicked: archives, resources in conflict, pairs, resources in identical copy, resources that replace the base game.
  • The filter field takes the name of a mod, of an archive, or part of a resource path (at least three letters).
  • Identical copy: two archives ship the same resource, byte for byte. It does not matter which one wins; they are counted apart.
  • Base game: the resource replaces a file of the game itself. That is the purpose of many mods; the information is useful when two mods replace the same one.
  • Archives installed by hand, outside Red Stack, count too; they are marked “outside Red Stack”.

Changing the load order

Archives load in the order of their names, character by character: ! and # first, then digits, CAPITALS, _, lower case. REDmod archives come after. A file archive\pc\mod\modlist.txt, if it exists, imposes its order.

In the “per archive” reading, unfold an archive: Move ahead… on the one that wins against it, Move behind… on the one it beats. Two ways to choose from:

  • Rename in the game: Red Stack proposes a name as close as possible to the target (often a prefix). The zip is not touched, the profile records the name, and Restore the author's name cancels it. If the old name is quoted in the code of the repository, you are told before.
  • Hold the order with modlist.txt: no name changes. The profile records the wanted order, “Apply” writes the file (the old one is copied to the backups). “Stop holding it” removes it at the next “Apply”.

In both cases only the profile is written: read the plan preview, then apply.

REDmod archives cannot be reordered here. An archive outside Red Stack cannot be renamed: only modlist.txt moves it.

Scripts and tweaks (code conflicts)

Scripts opens a separate analysis: the mods that step on each other in their code. The first reading takes a few dozen seconds, the following ones a few seconds. Read-only.

What is looked for

  • Redscript: two mods replace the same method (@replaceMethod); a wrapper (@wrapMethod) that does not call wrappedMethod and so cuts the chain.
  • TweakXL: the same property set to two values; an addition against a removal in a list; a record defined twice.
  • Hard-coded SetFlat: a value written by code against the tweak of another mod.

Three levels

to look atOnly one of the two can work: two different replacements of the same method.
to reviewProbably a problem, to be judged: opposite values, a wrapper that cuts, a duplicate.
no actionThe mods cross each other but stay compatible.
  • The chips filter by level and by sort; the field filters by mod, method, property or file.
  • An unfolded row explains the case and says who writes what. A click on file:line opens the file at that line in the editor; a click on the mod opens its detail.
  • Mods written to live together (@if(ModuleExists(…))) are recognised.
The “last word predicted” is deduced from the order of the file names. It is not observed in the game: take it as an indication. Not analysed: the Lua overlaps of CET (Override, Observe) and the .tweak files of the old format. Detection taken from Conflict Studio (MIT licence).

Mod items against a save

Items opens an analysis of its own: for each mod of the profile, the weapons, clothing and cyberware it adds to the game, and what a game save holds of them. A way to spot the item mods that are not used. Read only: nothing is written, neither in the game nor in the save.

  • The list at the top picks the save; by default, the most recent one of the saves folder (see Settings).
  • An item is owned if it is on V, in the stash or in the wardrobe. The wardrobe remembers a piece of clothing even once sold: it can still be worn as an appearance.
  • The chips count the mods with no item owned (first in the list), those partly used and those fully owned; a click shows only them. The kind buttons keep the weapons, the clothing or the cyberware.
  • An unfolded row lists the items of the mod, each with where the save holds it. A click on file:line opens the tweak that creates it; “Mod detail” opens its detail.
Items are read from the profile's TweakXL tweaks (.yaml). Not seen: items created by a .tweak file of the old format, by CET Lua or by Redscript. The kind of an item is deduced from what its record says about itself, then from the name of its base in the game: a rare base can stay out of the list. The save is read after the format described by WolvenKit (MIT licence), for game 2.0 and later.

History

History opens a panel: what Red Stack has written, action by action, from the most recent to the oldest.

  • Each “Apply” unfolds mod by mod: installed, removed, updated from such a version, modified.
  • The actions on the repository are there too: park, move into the stack, retire, delete a retired zip, rename, convert, rewrite a content, download an update, file an arrival.
  • Useful to answer “what has changed since the last time the game worked?”.

Store

The store holds one extracted tree per enabled mod. The game files are hard links to these trees: the same file has two names on the disk and takes its space only once.

Store opens a panel that says:

  • how many game files are linked and how many are copied (settings always are);
  • the real size on the disk, next to the one Windows Explorer adds up. Explorer counts a linked file twice, in the tree and in the game: its total is misleading, and that is normal;
  • the free space;
  • the trees with no enabled mod, with Purge…: they are deleted, the zips are not touched, and a tree is rebuilt from its zip;
  • the local edits: a file of a tree modified by hand. Undo… puts back the one from the zip; the game follows at “Apply”.
Put the store on the same disk as the game: a hard link does not cross disks. On another disk, Red Stack installs copies; everything works, but each mod takes its space twice.

Settings

Settings opens a full page. Almost everything is confirmed by Save, at the bottom; the first two sections, “Language” and “Theme”, and the action buttons (backups, reference, nxm:// links) act right away.

Language

  • The page, the side bar and the messages of Red Stack exist in eleven languages: French, English, German, Spanish, Brazilian Portuguese, Italian, Polish, Russian, Simplified Chinese, Japanese and Korean. Automatic follows the display language of VS Code; a language Red Stack does not have falls back to English.
  • All the texts of Red Stack, in its eleven languages, are written by an AI. French is the source language; the ten others, English included, are translations of it, checked by an automatic bench (values, tags, plural forms), not yet proofread by native speakers: a wrong or clumsy phrase can be reported with an issue on the project repository.
  • The choice applies right away: the page reloads in the new language. Save your other settings first, an entry in progress would be lost.
  • The messages of the engine (mod states, reasons, refusals, errors) follow this choice. A text kept in a cache before the change of language can stay in the old one until it is next read.
  • This manual exists in French and in English: it opens in French when Red Stack is in French, in English in any other language. The MCP servers (driving by a Claude Code session) speak English, whatever language is chosen; the names of their tools and the state codes stay those of the engine. The titles of the commands and settings in VS Code follow the language of VS Code, not this choice.

Theme

  • Two complete colour themes come with the extension: Red Stack Rouge (red) and Red Stack Jaune (yellow). A button activates each one, right away, for all your VS Code windows.
  • Other theme… opens the list of all installed themes (the one of Ctrl+K Ctrl+T), to go back to yours. The Red Stack page follows any theme.
  • Coloured activity bar icons: with a Red Stack theme, all the icons of the left bar take the accent colour, the same as the buttons; the active icon is recognised by its line. Unticked, only the active icon is coloured.

Folders

  • Repository and game: the only two that are required.
  • Store and game reference: left empty, they are placed next to the game folder (“… - Red Stack”, “… - Référence”). Backups and log: left empty, they go to the data folder.
  • Saves folder: the game saves, read by the Items tab, never written. Left empty: the game's folder in “Saved Games”.
  • New zips: unticked by default, a zip that arrived in a stack is left for you to tick. Ticked, it is enabled by default: all that remains is to apply.

Repository convention

How to read your layout: which folders are stacks, which subfolders are those of the parked, new (arrivals) and retired zips, which folders of a zip are never installed (documentation, sources). A button restores the default convention.

Red Stack reads three places and no more: the zips placed at the root of the repository, those of each stack, and those of the convention subfolders of a stack. A folder that holds archives and that the convention does not read (its name does not match the stack pattern, or it sits deeper inside a stack) is named under these fields, and on the list as long as it is empty: nothing is left out silently.

Convention for the content of zips

The tables of “Content…”: words kept as they are, prefixes by type, stacks where the full name of the mod is used.

Mod settings, never linked

Patterns of the settings files. A file that matches one is copied instead of being linked: what you set in game does not damage the tree of the mod and survives its update. The first reading of the game adds on its own what it finds modified.

Settings backups

  • Back up now: a dated copy of all the settings of the mods present in the game, shipped by a zip or written in game.
  • Compare with the game: what has changed since that backup.
  • Restore…: puts back the files that differ or are missing, with the game closed; today's files are copied first.

Outside Red Stack

The territory of a third-party installer (ReShade installs its shaders itself). Under these patterns, a file that is present and that Red Stack did not install is never linked, replaced or removed.

Before applying

A command run before any writing of the game (your own backup, for example). If it fails, nothing is written.

Game reference

  • Create the reference… copies the game without its archives (executables, libraries, base scripts). The files installed by Red Stack are left out of the copy: no need to empty the game first.
  • Check the base game says what has changed since; Restore the base game… puts it back, for example after an update forced by the launcher.

This machine

  • Python command and data folder (profiles, install registry, config.json).
  • nxm:// links: register Red Stack, or undo the registration.
  • MCP server: the command that declares it, to copy.

WolvenKit, for a Claude Code session

  • WolvenKit CLI: the folder that holds WolvenKit.CLI.exe (“WolvenKit Console”, to download separately from the WolvenKit releases page; it needs the .NET Runtime). The row says whether the CLI is found.
  • Workshop: the only folder this part writes to. A folder of its own, outside the game, the repository, the store, the backups and the data; otherwise everything is refused.
  • The command that declares this second server can be copied under the two fields. See Reading and rebuilding archives with WolvenKit.

Red Stack in VS Code

  • Side bar (Red Stack icon of the activity bar): the profile (click = change it), the enabled mods, what is waiting for “Apply”, the new zips, the conflicts, and a shortcut to each view, this manual included.
  • Tabs: the page, “Conflicts”, “Scripts and tweaks” and this manual are ordinary tabs. They can be moved, detached into a window, and they come back to their place when VS Code restarts.
  • Automatic refresh: the list re-reads itself when a zip arrives, leaves or changes in a stack, when archive\pc\mod changes, or when a profile is written elsewhere. It waits for a copy in progress to finish. The setting redStack.actualisationAuto turns it off; the ↻ button then re-reads on demand.
  • Searching this manual: the field of the contents filters the sections; Ctrl+F searches the text.

Driving by a Claude Code session

The extension carries an MCP server. Once declared (the command can be copied from “Settings”, “This machine”), a Claude Code session can read the state, the conflicts, the history, change a profile and prepare a plan.

What a session can do

  • Read: the state of the mods (by stack, by state, by kind), the detail of a mod, which mod owns a game file, the plan, the archive conflicts (per pair, per mod, per archive, per resource), the script and tweak conflicts, the load order, the history, the store, the game reference, the settings backups, the updates proposed by Nexus, the requirements of each mod (listed on Nexus or deduced from its files), the arrivals and the name each would take, the content of a zip against the convention.
  • Change a profile: enable or disable a mod or a stack, take or leave an option or a file, say “this file belongs to this mod”, set a priority between two mods or for a single file, rename in the game, change the load order, answer a FOMOD installer.
  • Set: the settings patterns and the “outside Red Stack” patterns, ignore or propose again the updates of a mod, make a settings backup.

What stays yours

  • Writing the game: applying a plan, restoring settings or the reference.
  • Writing the repository: park, move into the stack, retire, rename or convert an arrival, file an update, rewrite the content of a zip, download from Nexus, purge the store. A session prepares these actions by reading and tells you what to do; you do them in the page.
A session never writes the game. It leaves a request; VS Code shows you the plan with its figures and its reason, and you are the one who applies or refuses, through the same confirmation as the button of the page. The Nexus API key is never given to it.

Reading and rebuilding archives with WolvenKit

A second MCP server, declared separately, lets a Claude Code session open the archives of the game and of the mods with the WolvenKit CLI: useful to understand a conflict, compare the resource of a mod with that of the game, edit a file or rebuild an archive. It only serves a session; the page does not change.

To use it

  1. In “Settings”, “WolvenKit” section, name the folder of the CLI and a workshop folder, then “Save”.
  2. Copy the command of that section and run it once in a terminal.

What a session can do

  • Search for a resource by words of its path, in the base game, Phantom Liberty and the installed mods, and know which archives hold it.
  • List an archive, or the archives of a mod named as in Red Stack.
  • Extract resources as they are, export a texture as an image or a mesh as .glb, read a game file (.ent, .app, .mesh, .inkatlas…) as JSON.
  • Edit a game file brought into the workshop: change a value, add, remove or duplicate an element. The CLI rebuilds the file, then reads it back, and the session knows whether everything it wrote is there. The first original is kept in the _avant folder of the workshop.
  • Import an image or a .glb of the workshop as a game file.
  • Pack a folder of the workshop into an .archive, or build a WolvenKit project (.cpmodproj) stored in the workshop. On request, a zip in the form of a mod is made beside it.

Trying in game what a session has made

The archive and the zip stay in the workshop. To try them, drop the zip yourself in the arrival folder of a stack, tick the mod in the list, then “Plan preview” and “Apply”: the mod is then disabled and removed like any other.

Its safeguards

  • It only writes in the workshop. Not the game, not the repository, not the store. Putting an edited file in the game stays your action: a zip in a stack, then “Apply”.
  • It only builds from the workshop. The file to edit, the folder to pack and the project to build must be there: nothing is packed from the game or the repository.
  • An edit is all or nothing. One operation refused, and the file stays as it was. The working JSON files placed next to the files do not go into the archive.
  • A pattern that would take everything is refused (empty, *, *.*, fewer than three characters).
  • Files are counted before extracting. Above the ceiling (200 to extract, 40 to export, by default) nothing is written: the session receives the count and must narrow down.
Limits. An export does not follow the materials of a mesh stored in another archive. An edit goes through the WolvenKit JSON: it reads neither TweakDB nor the translated texts of the game. A built project is never installed in the game by this server. A search takes a few seconds per location.

Frequent questions

“Apply” refuses to write

  • The game is running: close it.
  • Conflicts to settle: the plan preview lists them; say which mod wins.
  • The plan has changed since the preview: the disk moved in the meantime. The new plan is shown; read it again.

The page stays on “Reading the repository and the game…” or says Python is missing

Without Python, the page says so: install it from python.org with “Add python.exe to PATH” ticked, then Try again; or Set the Python command… if Python is installed elsewhere (a full path works). The same command is set in “Settings”, “This machine” (or redStack.python). Version 3.11 or later is needed.

A mod is ticked but missing from the list of updates

Its zip does not carry the name of the Nexus site (mod number, version). Take it through Arrivals to rename it.

“Mod manager download” does nothing

No program is registered for nxm:// links on the machine: see nxm:// links.

The store folder “weighs” as much as the game

Explorer counts linked files twice. The Store panel gives the real size.

I changed a setting in game, will it be overwritten?

No. A file modified in game is kept as it is and marked “modified in game”; the plan preview says how many are in that case.

I want to remove Red Stack

The game files are real files (hard links): the game works without the extension. Only delete the store after disabling the mods and applying, or accept that the files stay in the game as ordinary files. Undo the nxm:// registration from “Settings” before uninstalling.

Glossary

ApplyThe only action that writes the game, always after a preview and a confirmation.
ArchiveAn .archive file of archive\pc\mod. It contains resources.
ArrivalAn archive that has just entered the repository and is not filed in a stack yet.
ConventionThe way your repository is filed and named; it can be set.
DisabledAn unticked mod.
Outside Red StackA file or folder that another installer manages, and that Red Stack leaves alone.
(Hard) linkA second name for the same file on the disk: no duplicate space.
ParkedA zip set aside in its stack: kept, not installable.
Install registryThe memory of Red Stack: which game file comes from which zip.
ResourceA file contained in an archive (mesh, texture…).
RetiredA zip set aside and kept in the retired folder of its stack: the old version an update replaces, or a zip you retire yourself. Nothing there is ever erased by Red Stack.
Core / base gameIn the list, “core”: a mod that others depend on. In “Game reference”, “base game”: the files of the game itself.
