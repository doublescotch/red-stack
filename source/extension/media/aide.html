Le principe en une minute

Red Stack est un gestionnaire de mods pour Cyberpunk 2077 qui vit dans VS Code. Il part d'une idée simple : votre dossier de zips est la bibliothèque. Vous rangez vos téléchargements comme vous voulez ; Red Stack les lit là où ils sont, sans les copier ailleurs ni les réorganiser.

Cinq mots suffisent à comprendre tout le reste :

DépôtLe dossier où vous gardez les zips de vos mods.
PileUn sous-dossier du dépôt (par exemple 1_Core, 12_Weapons). La page montre une table par pile.
ProfilLa liste de ce que vous voulez dans le jeu : quels mods sont actifs, quelles options et quels fichiers de chacun. Vous pouvez en avoir plusieurs.
MagasinUn dossier de travail où chaque mod actif est extrait dans son propre arbre. Les fichiers du jeu sont des liens vers ces arbres : un mod ne pèse qu'une fois sur le disque.
PlanLa différence entre ce que le profil veut et ce que le jeu contient : ce qui serait posé, remplacé, retiré.
La règle qui ne change jamais. Cocher une case n'écrit que le profil. Le jeu n'est écrit que par Appliquer, après que vous avez lu l'aperçu du plan et confirmé, et seul le plan que vous avez vu est appliqué. Tout geste qui écrit le dépôt ou le jeu se confirme dans une liste en haut de VS Code, dont le premier choix, actif d'office, est « Ne rien écrire ».

Mise en route

  1. Python 3.11 ou plus récent doit être installé sur le poste : le moteur de Red Stack est un script Python livré dans l'extension. Rien d'autre à installer. Red Stack essaie python, puis py -3 et python3 ; s'il n'en trouve aucun, la page le dit et offre de le télécharger ou d'indiquer sa commande.
  2. Ouvrez la page : icône Red Stack de la barre d'activité (à gauche), bouton « Red Stack » de la barre d'état (en bas), ou commande Red Stack : ouvrir (Ctrl+Maj+P).
  3. Au premier lancement, la page « Réglages » demande deux dossiers : votre dépôt de zips et le dossier du jeu. Enregistrez.
  4. La page propose alors de lire le jeu pour créer le profil « actuel ». Cette lecture n'écrit rien : elle reconnaît dans le jeu les fichiers de vos zips et coche les mods qui y sont déjà.
  5. Lisez l'Aperçu du plan. Sur un jeu déjà moddé, le premier plan remplace surtout des copies par des liens vers le magasin. Appliquer, jeu fermé.

Ensuite, la routine tient en trois gestes : cocher ou décocher, lire le plan, appliquer.

Si votre dépôt ne suit pas l'organisation attendue (quels dossiers sont des piles, où vont les zips parqués ou nouveaux), elle se règle : voir Réglages, « Convention du dépôt ». Des zips en vrac dans un seul dossier conviennent aussi : ceux qui sont posés à la racine même du dépôt sont lus comme une pile de plus, « (racine du dépôt) ».

La liste des mods

La page s'ouvre sur la liste : une table par pile, une ligne par zip.

L'en-tête

  • Profil : le profil montré. Nouveau… copie le profil courant sous un autre nom, Supprimer efface le fichier du profil (le jeu ne change pas).
  • Filtrer les mods… : filtre par nom, au fil de la frappe.
  • À quel mod est ce fichier ? : tapez un bout du chemin d'un fichier du jeu, puis Entrée. Red Stack dit quel mod l'a posé.
  • Arrivages, Mises à jour, Historique, Magasin : la gestion du dépôt.
  • Conflits, Scripts : les deux analyses, chacune dans son onglet.
  • Réglages, ? (ce manuel), ↻ (relire maintenant ; son survol dit l'heure de la dernière lecture), Aperçu du plan.

Les cases

  • La case d'une ligne active ou coupe un mod. La case d'un titre de pile active ou coupe toute la pile.
  • Vous pouvez cocher plusieurs mods à la suite : Red Stack attend un court silence, puis joue toutes vos coches ensemble et relit l'état une seule fois. Aucune coche n'est défaite en route.
  • Pendant qu'un geste écrit (parquer, remonter, retirer, renommer, appliquer…), un bandeau le dit et la page est verrouillée de la confirmation à la fin du geste : rien ne se coche ni ne se clique. Elle se rouvre seule.
  • Un clic sur le titre d'une pile la plie ou la déplie. Un clic sur une ligne ouvre le détail du mod.

La colonne « État »

poséActif, et le jeu porte ses fichiers. « (modifié en jeu) » : un de ses réglages a changé depuis la pose ; il est gardé tel quel.
à poserActif au profil, pas encore dans le jeu. Attend « Appliquer ».
à compléterDéjà posé, mais le plan a encore des fichiers à poser ou à remplacer pour lui (option ajoutée, nouvelle version).
coupé, à retirerDécoché, ses fichiers sont encore dans le jeu. Attend « Appliquer ».
coupéDécoché par vous, sorti du jeu.
jamais poséConnu du profil, jamais entré dans le jeu.
nouveau dans le dépôtZip arrivé dans une pile, que le profil ne connaît pas encore. Décoché d'office (réglable).
parqué, retiréZip rangé dans le dossier des parqués ou des retirés de sa pile : visible, pas posable tant qu'il n'est pas remonté.

La colonne « Nature »

Ce que le zip pose, lu dans son contenu : archive, xl (ArchiveXL), REDmod, scripts (Redscript), tweaks (TweakXL), CET, RED4ext, asi, audio, ReShade, réglages, autre. Un clic sur une puce filtre la liste sur cette nature ; un second clic rend tout.

Socle désigne un mod dont d'autres dépendent : il livre un chargeur (CET, RED4ext, Redscript, ArchiveXL, TweakXL, Codeware), ou d'autres mods du dépôt l'appellent dans leur code. Limite : un socle utilisé sans appel lisible dans le code n'est pas reconnu comme tel.

Pastilles, puces et tris

  • ▼ ▲ sur une ligne : ce mod perd ou gagne des ressources contre d'autres archives. ⇄ : ses propres archives se recouvrent entre elles. Le survol détaille, le clic ouvre l'analyse des conflits sur ce mod.
  • La puce FOMOD signale un zip posé par son installateur.
  • Les puces sous l'en-tête filtrent par état ; la ligne de chiffres résume le profil. Nouveaux montre les zips des dossiers d'arrivée et ceux de la pile que le profil ne connaît pas encore ; Parqués et Retirés montrent le contenu des dossiers des parqués et des retirés.
  • Un clic sur un en-tête de colonne trie ; le troisième clic rend l'ordre du dépôt.
  • ⇕ Tout plier / déplier, sur la ligne des chiffres, replie toutes les piles d'un coup ; si tout est déjà replié, il déplie tout. Dans « Mises à jour » et « Arrivages », il replie les bandes de pile. Le même bouton replie les lignes des onglets « Conflits » et « Scripts et tweaks », et un ⇕ en tête d'un volet fait de même pour ses lignes (historique, plan, dossiers du détail d'un mod).
  • Détail d'un mod : ses fichiers sont triés par chemin. Ceux d'un pack, ou d'un mod de plus de quarante fichiers, sont rangés par dossiers repliables, chacun avec son compte de fichiers pris ; un dossier déplié le reste quand la liste se redessine. Un fichier décoché dont un autre dossier du même zip pose la même cible est dit « tenu par un autre dossier de ce zip » : rien ne sort du jeu.
  • Largeur du volet : glissez le bord entre la liste et le volet pour l'élargir ou le rétrécir ; un double-clic sur ce bord revient à la largeur d'origine. La largeur est gardée.
  • Noms complets montre le nom entier du zip au lieu du titre lu dans un nom de téléchargement Nexus. Dossiers montre où se trouve un zip parqué, nouveau ou retiré. Natures montre ou cache la colonne « Nature » : décochée, elle rend sa largeur aux noms.
  • En bout de ligne : parquer un mod coupé et sorti du jeu ; pour un zip rangé (arrivé, parqué, retiré), remonter dans la pile, parquer un arrivage, ou retirer (la corbeille) : le zip passe dans le dossier des retirés de sa pile. Chaque geste est confirmé et n'est qu'un déplacement du zip dans sa pile : rien n'est effacé, un zip retiré se remonte depuis le filtre « Retirés ». Dans ce filtre seulement, la corbeille supprime le zip : il quitte le dépôt pour la corbeille de Windows. Les choix du mod restent au profil pour son retour.
  • Plusieurs zips rangés d'un coup : dans les filtres « Nouveaux », « Parqués » et « Retirés », chaque zip rangé porte une case, et la case d'une pile coche tous ceux de la pile montrés à l'écran. Ces cases ne touchent jamais le profil ni le plan. Dès qu'un zip est coché, les boutons Remonter dans la pile…, Parquer…, Retirer…, Supprimer… (zips retirés seulement) et « Tout décocher » apparaissent à droite des puces ; le lot part en une seule confirmation, et les cases restent cochées jusqu'à la fin du geste.

Les profils

Un profil est un fichier qui dit ce que vous voulez dans le jeu. Changer de profil ne change que ce que la page montre : le jeu suit quand vous appliquez le plan de ce profil.

  • Le profil garde, pour chaque mod : actif ou non, les options d'un pack, les fichiers pris un à un, les choix d'un installateur FOMOD, les noms changés dans le jeu, les priorités entre mods et l'ordre de chargement voulu.
  • Nouveau… part toujours d'une copie du profil courant : pratique pour essayer un lot de mods sans perdre l'état qui marche.
  • Passer d'un profil à l'autre revient à lire le plan (ce qui entre, ce qui sort) puis à appliquer. Grâce aux liens, cela prend quelques secondes même pour des centaines de mods.

Le détail d'un mod

Un clic sur une ligne ouvre le détail : tout ce que le zip contient, où chaque fichier va dans le jeu et dans quel état il s'y trouve.

États d'un fichier

liéLe fichier du jeu est un lien vers l'arbre du mod dans le magasin.
copiéPosé en copie : c'est le cas des réglages (pour qu'ils survivent à une mise à jour) et des fichiers en territoire d'un installateur tiers.
partagé avec XUn autre mod actif livre le même fichier, à l'identique : il reste dans le jeu tant que l'un des deux est actif.
écrasé par XUn autre mod actif livre un fichier différent au même endroit, et c'est le sien qui est posé.
modifié en jeuLe fichier a changé depuis sa pose (un réglage écrit par le jeu ou par vous). Il est gardé, jamais remplacé en silence.
hors Red StackLe fichier est en territoire d'un installateur tiers (ReShade…) et Red Stack ne l'a pas posé : il n'y touche pas.

Choisir ce qu'on prend

  • Pack à options : un zip qui range ses variantes dans des dossiers les montre comme des options à cocher.
  • Une case par fichier : prendre ou laisser un fichier seul. Le jeu ne change qu'à « Appliquer ».
  • « Ce fichier est à ce mod » : sur un fichier « hors Red Stack », cocher la case dit que ce fichier appartient au mod. Red Stack l'inscrit à son registre sans le modifier, et il partira avec le mod quand vous le couperez. Décocher le rend à l'installateur tiers et le laisse dans le jeu.
  • Priorité entre deux mods : quand deux mods actifs veulent le même fichier avec un contenu différent, le plan s'arrête sur un conflit à trancher. Vous dites lequel gagne, fichier par fichier ou pour tout le mod ; le profil s'en souvient.

Les boutons du détail

  • Installateur… : les pages de choix d'un FOMOD.
  • Noms dans le jeu… : poser les fichiers du mod sous d'autres noms, sans toucher au zip.
  • Renommer le contenu… : récrire le zip avec des noms à votre convention.
  • Conflits d'archives… : l'analyse des conflits, centrée sur ce mod.
  • Le lien Nexus ouvre la page du mod quand le nom du zip porte son numéro.

Aperçu du plan et « Appliquer »

Aperçu du plan compare le profil au jeu et liste ce qui serait fait, sans rien écrire :

à poserFichiers absents du jeu, qu'un mod actif apporte.
à remplacerFichiers présents avec un autre contenu (nouvelle version, autre mod prioritaire).
à retirerFichiers d'un mod coupé, que plus aucun mod actif ne livre.
à lier / à délierUne copie identique devient un lien vers le magasin, ou l'inverse (un fichier devenu réglage ou passé en territoire tiers). Le contenu du jeu ne change pas. Après une mise à jour, les fichiers restés identiques d'une version à l'autre sont « à lier » : ils passent à l'arbre de la nouvelle version, rien n'est copié. Un « à lier » repris d'un autre mod dit lequel. Sous chaque mod du plan, « Voir les fichiers » liste un par un les fichiers touchés ; le bloc des choix faits se replie d'un clic sur son titre. La fiche d'un mod en cours de mise à jour dit « à remplacer » ou « inchangé depuis la version d'avant » au lieu de nommer sa propre ancienne version.
pris / renduFichier inscrit au registre par « ce fichier est à ce mod », ou rendu à l'installateur tiers.
modlist.txtLe fichier d'ordre de chargement à écrire ou à retirer, si le profil le tient.
conflitsDeux mods actifs veulent le même fichier, contenu différent, sans priorité dite. À trancher avant d'appliquer.
mods coupésUne ligne par mod coupé : ce qui sort du jeu, ce qu'un autre mod reprend à l'identique, ce qu'un autre tient déjà.

Appliquer

  • Appliquer au jeu… ouvre une liste en haut de VS Code. Le premier choix, « Ne rien écrire », est actif d'office : Entrée tout seul n'écrit jamais le jeu. Il faut descendre sur « Appliquer » puis valider.
  • Le jeu doit être fermé. S'il tourne, rien n'est écrit.
  • Si le disque a changé entre l'aperçu et le clic, le plan n'est plus celui que vous avez vu : rien n'est écrit et le nouveau plan vous est montré.
  • Un fichier modifié en jeu depuis sa pose (un réglage, le plus souvent) est gardé tel quel : le plan le compte à part et « Appliquer » ne le remplace pas.
  • Fichier présent mais pas posé par Red Stack : le jeu porte déjà ce fichier, que Red Stack n'y a pas mis, avec un autre contenu que celui du zip (un mod installé à la main dans une autre version, par exemple). Il est laissé en place. Pour prendre celui du zip, dépliez cette ligne du plan : Remplacer par le zip sur un fichier, ou Tout remplacer par les zips. Le fichier passe alors dans « à remplacer » ; à l'application, l'ancien est d'abord copié dans le dossier des sauvegardes. Laisser en place revient en arrière tant que rien n'est appliqué.
  • Reprendre un mod installé à la main : déposez son zip dans le dossier d'arrivée de sa pile, remontez-le, cochez-le, ouvrez l'aperçu du plan. Les fichiers identiques sont repris sans rien écrire ; les autres se remplacent comme ci-dessus.
  • La commande « Avant d'appliquer » des Réglages, si vous en avez mis une, est lancée d'abord ; si elle échoue, rien n'est écrit.

Arrivages

Arrivages montre ce qui vient d'entrer dans le dépôt : les archives des dossiers d'arrivée de chaque pile, les zips qui portent encore un nom de l'application Nexus, et les .7z / .rar. Les lignes sont rangées par pile, dans l'ordre de la liste des mods ; un clic sur la bande d'une pile la replie ou la déplie.

Mettre les noms à la forme du site

  • Red Stack propose pour chaque archive le nom que donne le site Nexus : Nom-numéroDuMod-version-horodatage.zip. Il le lit par l'API publique de Nexus, sans clé, et garde la réponse six heures (Relire Nexus la redemande).
  • C'est ce nom qui permet ensuite de chercher les mises à jour.
  • Le nom proposé se retouche dans son champ. Quand plusieurs fichiers du mod conviennent, la ligne est « à trancher » avec la liste des candidats.
  • Cochez les lignes, puis Renommer les archives cochées…. Seul le nom du fichier change.

Convertir, remonter, parquer

  • Convertir en .zip… : un .7z ou un .rar est récrit en .zip (par 7-Zip, UnRAR ou le tar de Windows), relu, puis l'original est supprimé.
  • Remonter dans la pile… : le zip quitte le dossier d'arrivée et devient un mod « nouveau dans le dépôt », à cocher dans la liste.
  • Parquer… : le zip va dans le dossier des parqués de sa pile.
  • « Remonter les cochées » et « Parquer les cochées » traitent un lot en une seule confirmation.

Reconnaître une mise à jour

Quand un arrivage est une version plus récente d'un mod déjà en place, la ligne le dit. Ranger la mise à jour… met le nouveau zip à la place de l'ancien, qui part dans les retirés de sa pile ; le profil suit la nouvelle version. « À la place de… » permet de désigner un autre zip du même mod. Ce geste ne demande aucune clé d'API : il suffit de télécharger le fichier à la main dans un dossier d'arrivée.

Mod sans numéro Nexus (mod maison, zip venu de GitHub) : Red Stack le reconnaît à son nom et à sa version. Un arrivage Mon Mod 1.0.1.zip est proposé comme mise à jour de Mon Mod 1.0.0.zip (espaces, tirets et majuscules ne comptent pas ; la version doit être plus haute). Le nouveau zip garde son nom. Ces zips n'apparaissent pas dans « Mises à jour », qui ne lit que Nexus.

Désigner vous-même le zip remplacé : quand Red Stack ne reconnaît rien (nom changé, pas de version dans le nom), la liste Ranger à la place de… de la ligne propose tous les zips en place de la même pile. Choisissez celui que l'arrivage remplace : rien n'est comparé, l'arrivage prend le nom du champ « Nom voulu », l'ancien zip part dans les retirés. Une confirmation précède l'écriture.

« Contenu… » : les noms à l'intérieur du zip

  • Contenu… propose de renommer ce que le zip livre (archives, .xl, dossiers de scripts et de tweaks) selon votre convention : mots capitalisés, nom du mod, dossier de tête inutile retiré.
  • Avant de proposer, Red Stack lit les références de tout le dépôt. Un nom cité en dur par du code, un dossier partagé avec un autre mod, un préfixe d'ordre de chargement sont gardés, avec la raison affichée.
  • Chaque chemin proposé se retouche. La proposition recommande, elle ne vous bloque pas.
  • Restructurer : un chemin retouché peut changer de dossier. Tapez-le en entier (r6/tweaks/Famille/Mon_Mod.yaml) : un dossier qui n'existe pas est créé dans le zip. Rien ne vérifie ce que le mod attend à cet endroit ; à vous de le savoir.
  • Ajouter le dossier fait ce geste pour les scripts et les tweaks : le nom tapé dans « Dossier à ajouter » s'insère juste sous r6/scripts et r6/tweaks, dans tous les chemins de la table. Rien n'est écrit : vous relisez, puis vous renommez. Les archives ne sont pas concernées, le jeu ne les lit pas dans un sous-dossier.
  • Dossier de famille : quand au moins deux autres zips du dépôt au même début de nom (Famille - …) rangent leurs scripts ou leurs tweaks dans un même sous-dossier, Red Stack y propose ceux du nouveau venu, et le dit.
  • Valider récrit le zip (mêmes fichiers, mêmes dates, nouveaux noms), le relit, puis remplace l'ancien. Si le mod est dans le jeu, le plan remplacera ses fichiers.
Ce geste est différent de « Noms dans le jeu… », qui ne touche pas au zip et note seulement au profil sous quel nom poser. « Contenu… » range votre dépôt ; « Noms dans le jeu… » règle un cas dans un profil.

Mises à jour (Nexus)

Mises à jour compare chaque zip nommé à la forme du site aux fichiers que son mod publie sur Nexus. La recherche ne demande aucune clé et ne télécharge rien. Les lignes sont rangées par pile, dans l'ordre de la liste des mods, puis par nom ; un clic sur la bande d'une pile la replie ou la déplie. Un zip sans numéro Nexus (mod maison) n'est pas comparé : sa nouvelle version se range depuis « Arrivages ».

Lire la liste

  • Mise à jour : un fichier plus récent, du même nom hors version et de la même catégorie. Cochée d'office.
  • À voir : cas douteux (fichier archivé par l'auteur, plusieurs candidats, variante pour un autre patch du jeu). Jamais cochée d'office ; la ligne liste les fichiers plus récents à choisir.
  • Un zip que vous avez annoté dans son nom (retouche maison) est proposé mais pas coché, avec un avertissement : la mise à jour remplacerait votre retouche.
  • Ignorer écarte un mod des recherches ; c'est réversible depuis la même vue.
  • Le nom du nouveau zip se retouche avant de télécharger.
  • Non comparés : les zips sans numéro de mod dans leur nom, et les mods publiés ailleurs que sur Nexus.

Télécharger

Le téléchargement demande votre clé d'API personnelle Nexus :

  1. Clé d'API Nexus… ouvre une saisie dans VS Code. Où la trouver ? ouvre la page des clés de votre compte : la clé personnelle est tout en bas de cette page, sous la liste des applications (« Personal API Key »).
  2. La clé est gardée dans le coffre de VS Code. Elle n'est écrite dans aucun fichier et n'est jamais donnée au serveur MCP. Un champ vide l'oublie.
  3. Cochez, puis Télécharger… : une confirmation pour le lot, puis les zips arrivent un par un.
  • Chaque nouvelle version prend la place de l'ancienne, qui part dans le dossier des retirés de sa pile. Le profil suit. Il reste à lire l'aperçu du plan et à appliquer.
  • Compte Premium : lien direct, rien d'autre à faire.
  • Compte gratuit : Nexus réserve le lien direct aux comptes Premium. Pour chaque zip, Red Stack ouvre la page du fichier ; vous cliquez « Mod manager download » (ou « Slow download »). Le lien arrive seul si Red Stack est inscrit pour les liens nxm:// ; sinon vous le collez dans la boîte ouverte en haut de VS Code.
  • Pendant un téléchargement, la vue est verrouillée (un lot à la fois) et les zips concernés ne se parquent ni ne se récrivent. Le reste de l'outil reste libre.
Le quota d'appels à l'API est attaché à votre clé, donc à votre compte. La puce de votre compte, au survol, dit ce qu'il en reste.

Liens nxm:// (« Mod manager download »)

Sur Nexus, le bouton « Mod manager download » envoie un lien nxm:// au gestionnaire de mods inscrit sur le poste. Red Stack peut être ce gestionnaire (Windows).

  1. Réglages, section « Ce poste » : la page dit quel programme reçoit ces liens aujourd'hui.
  2. Recevoir les liens nxm:// dans Red Stack… (confirmé) écrit une clé du registre de votre compte Windows, sans droits d'administrateur. Le programme d'avant est noté.
  3. Ne plus recevoir les liens nxm://… défait l'inscription et rend la main au programme d'avant.

Une fois inscrit, un clic sur « Mod manager download » ouvre dans VS Code une liste à choix :

  • Mettre à jour tel zip du dépôt : le fichier reçu est du même mod. La nouvelle version prend sa place.
  • Mod nouveau : choisissez la pile ; le zip est rangé dans son dossier d'arrivée et paraît dans Arrivages.
  • Ne rien télécharger, choix actif d'office.

La clé d'API reste nécessaire : Nexus ne délivre pas le fichier sans elle, même avec le lien.

Installateurs FOMOD

Un zip qui porte fomod/ModuleConfig.xml décrit lui-même ses choix d'installation. Red Stack rejoue cet installateur.

  • Dans le détail du mod, Installateur… ouvre un volet avec ses pages, ses groupes (un seul choix, ou plusieurs), les descriptions, et les images à la demande.
  • Un clic note le choix au profil. Les pages et les fichiers qui dépendent d'un choix suivent aussitôt ; une page écartée par un choix d'avant est dite cachée.
  • Les fichiers que l'installateur copie hors des dossiers du jeu (documentation, outils) sont posés d'office, comme le ferait tout installateur ; une case permet de les laisser.
  • « Ignorer l'installateur : piocher à la main » rend le zip aux cases par fichier. Suivre l'installateur y revient.
  • Comme toujours, le jeu ne change qu'à « Appliquer ».
Limites, dites aussi à l'écran. Une condition sur la présence d'un fichier dans le jeu est tenue pour « absent » ; une condition sur la version du jeu est tenue pour vraie.

Noms dans le jeu

Noms dans le jeu… (détail d'un mod) pose ce que le mod livre sous d'autres noms : archives, .xl, fichiers et dossiers de r6\scripts et r6\tweaks, dossier CET, dossier REDmod.

  • Un champ par nom. Le zip ne change pas : le profil note le nom voulu ; « Appliquer » pose le nouveau et retire l'ancien. Un champ vidé rend le nom de l'auteur.
  • Chaque ligne dit qui cite ce nom dans le code du dépôt, le mod lui-même compris. Un nom cité est un nom que du code cherche tel quel : le renommer peut casser le mod qui le cite. Red Stack prévient, sans vous bloquer.
  • Refusés : un changement de casse seul, et un nom qui prendrait la place du fichier d'un autre mod actif.
  • Un dossier CET renommé laisse ses réglages écrits en jeu sous l'ancien nom.

Usage courant : changer la place d'une archive dans l'ordre de chargement (voir plus bas), ou ranger les dossiers de scripts d'une famille de mods.

Conflits d'archives

Plusieurs archives peuvent livrer la même ressource (un maillage, une texture). Le jeu prend chaque ressource dans la première archive chargée qui la contient. Une archive gagne donc sur celles chargées après elle et perd contre celles d'avant.

À l'écran, « archive » désigne le fichier .archive et « ressource » ce qu'il contient.

Conflits ouvre l'analyse dans un onglet à côté de la page (il se détache en fenêtre par le clic droit sur son titre). C'est une lecture seule, faite sur l'ordre voulu par le profil ; une puce dit combien de changements d'archives restent à appliquer.

Quatre lectures

  • Par archive : pour chacune, sur qui elle gagne et contre qui elle perd, en nombre de ressources.
  • Par mod et par paire de mods : « A gagne sur B », avec « tout voir » pour la liste des ressources.
  • Chaque ligne dit combien de ressources le mod ou l'archive livre, et combien sont encore servies au jeu. Ligne dépliée, Toutes ses ressources… ajoute la liste de celles qui sont hors conflit : il est seul à les livrer, le jeu les prend donc chez lui. Un second clic la cache.
  • Par paire d'archives.
  • Par ressource : dans quelle archive elle est prise, par lesquelles elle est perdue.
  • Les puces de chiffres se cliquent : archives, ressources en conflit, paires, ressources en copie identique, ressources qui remplacent le jeu de base.
  • Le champ de filtre prend un nom de mod, d'archive, ou un bout de chemin de ressource (trois lettres au moins).
  • Copie identique : deux archives livrent la même ressource, octet pour octet. Peu importe laquelle gagne ; elles sont comptées à part.
  • Jeu de base : la ressource remplace un fichier du jeu lui-même. C'est le but de beaucoup de mods ; l'information sert quand deux mods remplacent la même.
  • Les archives posées à la main, hors Red Stack, comptent aussi ; elles sont dites « hors Red Stack ».

Changer l'ordre de chargement

Les archives se chargent dans l'ordre de leurs noms, caractère par caractère : ! et # d'abord, puis les chiffres, les MAJUSCULES, _, les minuscules. Les archives REDmod viennent après. Un fichier archive\pc\mod\modlist.txt, s'il existe, impose son ordre.

Dans la lecture « par archive », dépliez une archive : Passer devant… sur celle qui gagne contre elle, Passer derrière… sur celle qu'elle bat. Deux voies au choix :

  • Renommer dans le jeu : Red Stack propose un nom au plus près de la cible (souvent un préfixe). Le zip n'est pas touché, le profil note le nom, et Rendre le nom de l'auteur l'annule. Si l'ancien nom est cité dans le code du dépôt, c'est dit avant.
  • Tenir l'ordre par modlist.txt : aucun nom ne change. Le profil note l'ordre voulu, « Appliquer » écrit le fichier (l'ancien est copié dans les sauvegardes). « Ne plus le tenir » le retire au prochain « Appliquer ».

Dans les deux cas seul le profil est écrit : lisez l'aperçu du plan, puis appliquez.

Les archives REDmod ne se réordonnent pas ici. Une archive hors Red Stack ne se renomme pas : seule modlist.txt la déplace.

Scripts et tweaks (conflits de code)

Scripts ouvre une analyse à part : les mods qui se marchent dessus dans leur code. La première lecture prend quelques dizaines de secondes, les suivantes quelques secondes. Lecture seule.

Ce qui est cherché

  • Redscript : deux mods remplacent la même méthode (@replaceMethod) ; une enveloppe (@wrapMethod) qui n'appelle pas wrappedMethod et coupe donc la chaîne.
  • TweakXL : la même propriété posée à deux valeurs ; un ajout contre un retrait dans une liste ; un enregistrement défini deux fois.
  • SetFlat en dur : une valeur écrite par du code contre le tweak d'un autre mod.

Trois niveaux

à regarderUn seul des deux peut marcher : deux remplacements différents de la même méthode.
à revoirProbablement gênant, à juger : valeurs opposées, enveloppe qui coupe, doublon.
sans actionLes mods se croisent mais restent compatibles.
  • Les puces filtrent par niveau et par sorte ; le champ filtre par mod, méthode, propriété ou fichier.
  • Une ligne dépliée explique le cas et dit qui écrit quoi. Un clic sur fichier:ligne ouvre le fichier à cette ligne dans l'éditeur ; un clic sur le mod ouvre son détail.
  • Les mods écrits pour cohabiter (@if(ModuleExists(…))) sont reconnus.
Le « dernier mot prévu » est déduit de l'ordre des noms de fichiers. Il n'est pas observé dans le jeu : prenez-le comme une indication. Ne sont pas analysés : les recoupements Lua de CET (Override, Observe) et les fichiers .tweak de l'ancien format. Détection reprise de Conflict Studio (licence MIT).

Historique

Historique ouvre un volet : ce que Red Stack a écrit, geste par geste, du plus récent au plus ancien.

  • Chaque « Appliquer » se déplie mod par mod : posé, retiré, mis à jour depuis telle version, modifié.
  • Les gestes sur le dépôt y sont aussi : parquer, remonter, retirer, supprimer un zip retiré, renommer, convertir, récrire un contenu, télécharger une mise à jour, ranger un arrivage.
  • Utile pour répondre à « qu'est-ce qui a changé depuis la dernière fois que le jeu marchait ? ».

Magasin

Le magasin porte un arbre extrait par mod actif. Les fichiers du jeu sont des liens physiques vers ces arbres : le même fichier a deux noms sur le disque et ne pèse qu'une fois.

Magasin ouvre un volet qui dit :

  • combien de fichiers du jeu sont liés et combien sont copiés (les réglages le sont toujours) ;
  • le poids réel sur le disque, à côté de celui que l'Explorateur de Windows additionne. L'Explorateur compte un fichier lié deux fois, dans l'arbre et dans le jeu : son total est trompeur, c'est normal ;
  • la place libre ;
  • les arbres sans mod actif, avec Purger… : ils sont supprimés, les zips ne sont pas touchés, et un arbre se refait depuis son zip ;
  • les retouches : un fichier d'un arbre modifié à la main. Annuler… remet celui du zip ; le jeu suit à « Appliquer ».
Mettez le magasin sur le même disque que le jeu : un lien physique ne traverse pas les disques. Sur un autre disque, Red Stack pose des copies ; tout marche, mais chaque mod pèse deux fois.

Réglages

Réglages ouvre une page pleine. Presque tout se valide par Enregistrer, en bas ; les deux premières sections, « Langue » et « Thème », et les boutons d'action (sauvegardes, référence, liens nxm://) agissent tout de suite.

Langue

  • La page, la barre latérale et les messages de Red Stack existent en onze langues : français, anglais, allemand, espagnol, portugais du Brésil, italien, polonais, russe, chinois simplifié, japonais et coréen. Automatique suit la langue d'affichage de VS Code ; une langue que Red Stack n'a pas passe en anglais.
  • Tous les textes de Red Stack, dans ses onze langues, sont écrits par une IA. Le français est la langue source ; les dix autres, anglais compris, en sont des traductions, contrôlées par un banc automatique (valeurs, balises, formes du pluriel), pas encore relues par des locuteurs : une tournure fausse ou maladroite se signale par un ticket sur le dépôt du projet.
  • Le choix s'applique tout de suite : la page se recharge dans la nouvelle langue. Enregistrez d'abord vos autres réglages, une saisie en cours serait perdue.
  • Les messages du moteur (états des mods, raisons, refus, erreurs) suivent ce choix. Un texte gardé dans un cache avant le changement de langue peut rester dans l'ancienne jusqu'à sa prochaine relecture.
  • Ce manuel existe en français et en anglais : il s'ouvre en français quand Red Stack est en français, en anglais dans toute autre langue. Les serveurs MCP (pilotage par une session Claude Code) parlent anglais, quelle que soit la langue choisie ; les noms de leurs outils et les codes d'état restent ceux du moteur. Les titres des commandes et des réglages dans VS Code suivent la langue de VS Code, pas ce choix.

Thème

  • Deux thèmes de couleurs complets viennent avec l'extension : Red Stack Rouge et Red Stack Jaune. Un bouton active chacun, tout de suite, pour toutes vos fenêtres VS Code.
  • Autre thème… ouvre la liste de tous les thèmes installés (celle de Ctrl+K Ctrl+T), pour revenir au vôtre. La page Red Stack suit n'importe quel thème.
  • Icônes de la barre d'activité en couleur : avec un thème Red Stack, toutes les icônes de la barre de gauche prennent la couleur d'accent, la même que celle des boutons ; l'icône active se reconnaît à son trait. Décochée, seule l'icône active est en couleur.

Dossiers

  • Dépôt et jeu : les deux seuls obligatoires.
  • Magasin et référence du jeu : vides, ils se placent à côté du dossier du jeu (« … - Red Stack », « … - Référence »). Sauvegardes et journal : vides, ils vont dans le dossier des données.
  • Zips nouveaux : décochée d'office, un zip arrivé dans une pile reste à cocher. Cochée, il est activé d'office : il ne reste qu'à appliquer.

Convention du dépôt

Comment lire votre organisation : quels dossiers sont des piles, quels sous-dossiers sont ceux des zips parqués, nouveaux (arrivages) et retirés, quels dossiers d'un zip ne sont jamais posés (documentation, sources). Un bouton remet la convention par défaut.

Red Stack lit trois endroits, pas plus : les zips posés à la racine du dépôt, ceux de chaque pile, et ceux des sous-dossiers de convention d'une pile. Un dossier qui porte des archives et que la convention ne lit pas (son nom ne suit pas le motif des piles, ou il est rangé plus bas dans une pile) est nommé sous ces champs, et sur la liste tant qu'elle est vide : rien n'est écarté en silence.

Convention du contenu des zips

Les tables de « Contenu… » : mots gardés tels quels, préfixes par type, piles où le nom complet du mod est repris.

Réglages des mods, jamais liés

Motifs des fichiers de réglages. Un fichier qui en suit un est copié au lieu d'être lié : ce que vous réglez en jeu n'abîme pas l'arbre du mod et survit à sa mise à jour. La première lecture du jeu ajoute seule ce qu'elle trouve modifié.

Sauvegardes des réglages

  • Sauvegarder maintenant : copie datée de tous les réglages des mods présents dans le jeu, livrés par un zip ou écrits en jeu.
  • Comparer au jeu : ce qui a changé depuis cette sauvegarde.
  • Restaurer… : remet les fichiers différents ou absents, jeu fermé ; ceux d'aujourd'hui sont copiés avant.

Hors Red Stack

Le territoire d'un installateur tiers (ReShade pose lui-même ses shaders). Sous ces motifs, un fichier présent que Red Stack n'a pas posé n'est jamais lié, remplacé ni retiré.

Avant d'appliquer

Une commande lancée avant toute écriture du jeu (votre propre sauvegarde, par exemple). Si elle échoue, rien n'est écrit.

Référence du jeu

  • Créer la référence… copie le jeu sans ses archives (exécutables, bibliothèques, scripts de base). Les fichiers posés par Red Stack sont laissés hors de la copie : inutile de vider le jeu d'abord.
  • Contrôler le socle dit ce qui a changé depuis ; Restaurer le socle… le remet, par exemple après une mise à jour forcée par le lanceur.

Pilotage par une session Claude Code

L'extension porte un serveur MCP. Une fois déclaré (la commande se copie depuis « Réglages », « Ce poste »), une session Claude Code peut lire l'état, les conflits, l'historique, changer un profil et préparer un plan.

Ce qu'une session peut faire

  • Lire : l'état des mods (par pile, par état, par nature), le détail d'un mod, à qui est un fichier du jeu, le plan, les conflits d'archives (par paire, par mod, par archive, par ressource), les conflits de scripts et de tweaks, l'ordre de chargement, l'historique, le magasin, la référence du jeu, les sauvegardes de réglages, les mises à jour proposées par Nexus, les arrivages et le nom que chacun prendrait, le contenu d'un zip face à la convention.
  • Changer un profil : activer ou couper un mod ou une pile, prendre ou laisser une option ou un fichier, dire « ce fichier est à ce mod », régler une priorité entre deux mods ou pour un seul fichier, renommer dans le jeu, changer l'ordre de chargement, répondre à un installateur FOMOD.
  • Régler : les motifs de réglages et les motifs « hors Red Stack », ignorer ou reproposer les mises à jour d'un mod, faire une sauvegarde des réglages.

Ce qui reste à vous

  • Écrire le jeu : appliquer un plan, restaurer des réglages ou la référence.
  • Écrire le dépôt : parquer, remonter, retirer, renommer ou convertir un arrivage, ranger une mise à jour, récrire le contenu d'un zip, télécharger depuis Nexus, purger le magasin. Une session prépare ces gestes en lecture et vous dit quoi faire ; vous les faites dans la page.
Une session n'écrit jamais le jeu. Elle dépose une demande ; VS Code vous montre le plan chiffré et son motif, et c'est vous qui appliquez ou refusez, par la même confirmation que le bouton de la page. La clé d'API Nexus ne lui est jamais donnée.

Lire et refaire des archives par WolvenKit

Un second serveur MCP, à déclarer à part, laisse une session Claude Code ouvrir les archives du jeu et des mods avec la CLI WolvenKit : utile pour comprendre un conflit, comparer la ressource d'un mod à celle du jeu, retoucher un fichier ou refaire une archive. Il ne sert qu'à une session ; la page ne change pas.

Pour s'en servir

  1. Dans « Réglages », section « WolvenKit », désignez le dossier de la CLI et un dossier d'atelier, puis « Enregistrer ».
  2. Copiez la commande de cette section et lancez-la une fois dans un terminal.

Ce qu'une session peut faire

  • Chercher une ressource par des mots de son chemin, dans le jeu de base, Phantom Liberty et les mods installés, et savoir quelles archives la portent.
  • Lister une archive, ou les archives d'un mod désigné par son nom dans Red Stack.
  • Extraire des ressources telles quelles, exporter une texture en image ou un mesh en .glb, lire un fichier du jeu (.ent, .app, .mesh, .inkatlas…) en JSON.
  • Retoucher un fichier du jeu amené dans l'atelier : changer une valeur, ajouter, retirer ou doubler un élément. La CLI refait le fichier, puis le relit, et la session sait si tout ce qu'elle a écrit y est. Le premier original est gardé dans le dossier _avant de l'atelier.
  • Importer une image ou un .glb de l'atelier en fichier du jeu.
  • Packer un dossier de l'atelier en .archive, ou construire un projet WolvenKit (.cpmodproj) rangé dans l'atelier. Sur demande, un zip à la forme d'un mod est fait à côté.

Essayer en jeu ce qu'une session a fabriqué

L'archive et le zip restent dans l'atelier. Pour les essayer, déposez vous-même le zip dans le dossier d'arrivée d'une pile, cochez le mod dans la liste, puis « Aperçu du plan » et « Appliquer » : le mod se coupe et se retire ensuite comme n'importe quel autre.

Ses gardes

  • Il n'écrit que dans l'atelier. Ni le jeu, ni le dépôt, ni le magasin. Mettre un fichier retouché dans le jeu reste votre geste : un zip dans une pile, puis « Appliquer ».
  • Il ne fabrique que depuis l'atelier. Le fichier à retoucher, le dossier à packer et le projet à construire doivent s'y trouver : rien n'est packé depuis le jeu ou le dépôt.
  • Une retouche est tout ou rien. Une opération refusée, et le fichier reste tel qu'il était. Les JSON de travail posés à côté des fichiers n'entrent pas dans l'archive.
  • Un motif qui prendrait tout est refusé (vide, *, *.*, moins de trois caractères).
  • Les fichiers sont comptés avant d'extraire. Au-dessus du plafond (200 pour extraire, 40 pour exporter, d'office) rien n'est écrit : la session reçoit le compte et doit resserrer.
Limites. Un export ne suit pas les matières d'un mesh rangées dans une autre archive. Une retouche passe par le JSON de WolvenKit : elle ne lit ni TweakDB ni les textes traduits du jeu. Un projet construit n'est jamais installé dans le jeu par ce serveur. Une recherche prend quelques secondes par lieu.

Questions fréquentes

« Appliquer » refuse d'écrire

  • Le jeu tourne : fermez-le.
  • Des conflits à trancher : l'aperçu du plan les liste ; dites quel mod gagne.
  • Le plan a changé depuis l'aperçu : le disque a bougé entre-temps. Le nouveau plan est montré ; relisez-le.

La page reste sur « Lecture du dépôt et du jeu… » ou dit que Python manque

Sans Python, la page le dit : installez-le depuis python.org en cochant « Add python.exe to PATH », puis Réessayer ; ou Indiquer la commande Python… si Python est installé ailleurs (un chemin complet convient). La même commande se règle dans « Réglages », « Ce poste » (ou redStack.python). Il faut la version 3.11 ou plus récente.

Un mod est coché mais absent de la liste des mises à jour

Son zip ne porte pas le nom du site Nexus (numéro du mod, version). Passez-le par Arrivages pour le renommer.

« Mod manager download » ne fait rien

Aucun programme n'est inscrit pour les liens nxm:// sur le poste : voir Liens nxm://.

Le dossier du magasin « pèse » autant que le jeu

L'Explorateur compte deux fois les fichiers liés. Le volet Magasin donne le poids réel.

J'ai modifié un réglage en jeu, va-t-il être écrasé ?

Non. Un fichier modifié en jeu est gardé tel quel et signalé « modifié en jeu » ; l'aperçu du plan dit combien sont dans ce cas.

Je veux retirer Red Stack

Les fichiers du jeu sont de vrais fichiers (des liens physiques) : le jeu marche sans l'extension. Ne supprimez le magasin qu'après avoir coupé les mods et appliqué, ou acceptez que les fichiers restent dans le jeu comme des fichiers ordinaires. Défaites l'inscription nxm:// depuis « Réglages » avant de désinstaller.
